# PennyWise → Cashew Feature-Gap Analysis

## Verdict on the hypothesis

**Mostly true, with four real gaps.** Cashew genuinely already has the heavy app surface — budgets, goals/loans, subscriptions & repeating transactions, categories, smart auto-categorization, multi-currency, accounts, sync/backup, home widgets, **and even its own notification-listener + Gmail capture pipeline** (`pages/autoTransactionsPageEmail.dart`). So the premise "we mainly need the capture pipeline" holds for the *UI/data model*. But PennyWise's value isn't just "capture exists" — it's **capture *quality***. The genuine ❌/🟡 gaps that matter are all in the capture layer's robustness: (1) the **155-bank deterministic SMS parser** (Cashew's matcher is a naive user-authored `contains` substring template that only fires while the app is foregrounded); (2) **deduplication** (Cashew has none for captured transactions); (3) the **unrecognized-SMS review queue** that feeds parser improvement; and (4) **bank-balance reconciliation** — Cashew's account balance is *derived* and silently drifts, while every transaction SMS already reports the true balance we could reconcile against. Everything else PennyWise has is either already in Cashew or maps cleanly onto an existing Cashew structure with light adaptation. Do **not** rebuild Cashew's budgets/goals/subscriptions/widgets/export — port the parser, dedup, review-queue, and balance-reconciliation, and *reuse* Cashew's tables for the rest.

## What to actually port (prioritized)

### 1. The 155-bank SMS parser (`parser-core`) — the whole reason this project exists  [L]
- **Why it matters:** This is the irreplaceable asset. Cashew's `ScannerTemplates` requires each user to hand-author brittle `contains`/before/after substrings per bank and only fires while the app is foregrounded — useless for reliable capture. PennyWise ships deterministic, tested parsers for 155 banks.
- **Maps onto Cashew via:** the **already-scaffolded plugin** (`packages/cashew_pennywise/`): vendor `parser-core` as an AAR, expose `parse`/`parseBatch` over MethodChannel, return a Dart `ParsedTransaction`. Captured transactions get inserted with `MethodAdded` — **add a new enum value `MethodAdded.parsed`** (currently `email, shared, csv, preview, appLink` at `tables.dart:122`) so captured rows are distinguishable from manual ones.
- **Approach:** Plugin returns `ParsedTransaction{amount,type,merchant,reference,accountLast4,balance,currency,bankName,transactionHash}`. A Dart orchestrator maps: `merchant` → `AssociatedTitles` lookup → `categoryFk`; `accountLast4` → `Wallet`; `currency` → wallet currency; inserts a `Transaction`. Keep `ScannerTemplates` as a fallback for senders the parser doesn't know.

### 2. Transaction deduplication  [M]
- **Why it matters:** Without it, dual SMS+notification capture, re-scans of the SMS inbox, and bank-duplicate SMS will create duplicate transactions — the fastest way to destroy user trust. Cashew has **zero** dedup for captured txns today.
- **Maps onto Cashew via:** add a nullable `transactionHash` text column to the `Transactions` table (UUID design already supports schema migration — bump `schemaVersionGlobal` per CLAUDE.md migration steps). Reuse PennyWise's `generateTransactionId()` (md5 of `sender|amount|bodyHash`).
- **Approach:** Before inserting a captured txn, query by hash; skip if present. Port the UPI-reference + 3-minute-window logic from `TransactionDeduplication.kt` for the SMS-vs-notification double-capture case. Also honor "previously deleted → don't re-add" (store deleted hashes; Cashew already has `DeleteLogs` to lean on).

### 3. Unrecognized-SMS review queue  [S–M]
- **Why it matters:** It's the feedback loop that keeps capture quality high — surfaces messages from known-financial senders the parser missed, so users (or upstream) can fix coverage. Directly improves #1 over time.
- **Maps onto Cashew via:** a small queue (table in the plugin, or a Cashew table mirroring `UnrecognizedSmsEntity`: sender, body, receivedAt, reported, isDeleted) surfaced in the existing **auto-transactions page** (`pages/autoTransactionsPageEmail.dart`), next to the template list.
- **Approach:** When `BankParserFactory` recognizes the *sender* (DLT -T/-S suffix or known bank) but `parse` returns null, enqueue. Let the user create a `ScannerTemplate` from it (bridge to Cashew's existing fallback matcher) or dismiss.

### 4. PDF statement import (GPay/PhonePe)  [M]
- **Why it matters:** Backfills history capture can't reach (pre-install, missed SMS). Distinct value, but not on the realtime-capture critical path.
- **Maps onto Cashew via:** already scoped as a pure-Dart port in the plugin (`lib/src/pdf/pdf_statement_parser.dart`, `pdfrx`). Imported rows insert as normal `Transactions` and run through the **same dedup (#2)** so they don't double with SMS-captured rows. Surface alongside `widgets/importCSV.dart`.
- **Approach:** Port `PdfParserFactory`/`GPayPdfParser`/`PhonePePdfParser` parse logic to Dart; feed results into the same insert+dedup+merchant-map orchestrator as #1.

### 5. Bank-balance reconciliation (account balance tracking)  [M]
- **Why it matters:** A derived balance is only as correct as the transactions feeding it. The moment one SMS is missed/unparsed, a cash spend happens, or a duplicate slips through, Cashew's wallet balance is wrong and stays wrong. Every bank transaction SMS already states the **true balance after the transaction** (`ParsedTransaction.balance`, plus `creditLimit` for cards) — using it turns the account balance from "best guess" into "bank-accurate, self-healing," and makes the balance line graph trustworthy. This is PennyWise's real edge on accounts; we already capture the data, we just need to use it.
- **Reuse, don't rebuild:** Cashew already has the two hard pieces — `createCorrectionTransaction(delta, wallet, …)` (a balance-correction txn, excluded from spending totals via `includeBalanceCorrection:false`) and `WalletDetailsLineGraph` (cumulative balance over time). No new balance table, no parallel `AccountBalanceEntity`.
- **What to add (small):**
  1. **Wallet ↔ bank-account identity** — nullable `bankName` + `accountLast4` on `Wallets` (one migration; bump `schemaVersionGlobal`). Lets a parsed `(bankName,last4)` route to the right wallet. (Many-cards-one-wallet can come later as a sidecar mapping table.)
  2. **Reconciliation step** — in the capture orchestrator, after inserting a parsed txn that carries a non-null `balance` for a mapped wallet: compute `delta = reportedBalance − cashewComputedBalance` (respect `Wallet.decimals` tolerance). If `|delta| > tolerance`, apply it via `createCorrectionTransaction(delta, wallet, title: "Bank balance", note: <sender/last4>, dateTime: txnTime)`.
- **Keep it quiet (avoid correction spam):** only correct when drift exceeds tolerance, and **update the most recent auto-reconciliation correction in place** (tag it, e.g. via a known `note`/title marker) rather than stacking a new one per SMS — so the wallet self-trues without flooding the transaction list. Corrections are already hidden from spending analytics.
- **Credit cards:** when `isFromCard`/credit, the reported figure is outstanding and `creditLimit` is *available* limit; reconcile the wallet to outstanding and optionally store available-limit for display. (v2 — debit/savings reconciliation first.)
- **Payoff for free:** because reconciliations are normal transactions, `WalletDetailsLineGraph` immediately reflects bank-true balance history — no separate time-series UI needed.

### Deferred / optional (only if capture quality demands it)
- **Mandate→subscription auto-create [M]:** when a parser yields `MandateInfo`, create a `TransactionSpecialType.subscription` txn. Reuse Cashew's repeating engine — do not add a subscription table.
- **Generic rule engine [M]:** only if you need amount/time/account conditions or **BLOCK** (drop spam/promo). For plain merchant→category, `AssociatedTitles` is enough.
- **Notification quick-actions [M]:** polish; Cashew's foreground add-flow is acceptable for v1.

## Already covered — do NOT rebuild

These PennyWise features Cashew already does as well or better. Wire the parser *into* them; don't reimplement.

- **Subscriptions & repeating transactions** — `TransactionSpecialType.subscription`/`repetitive`/`upcoming` + period/reoccurrence/endDate/notification engine (`tables.dart:44`, `pages/subscriptionsPage.dart`). Richer than `SubscriptionEntity`.
- **Merchant→category mapping** — `AssociatedTitles` (substring + exact-match, `getSimilarAssociatedTitles`) *is* `MerchantMappingEntity`. Reuse, don't add a table.
- **Loans / debt** — modeled as `Objectives` (`ObjectiveType.loan`) + `TransactionSpecialType.credit/debt` with remaining computed from opposite-polarity txns (`tables.dart:515`, CLAUDE.md). Covers PennyWise's `LoanEntity`.
- **Budgets (incl. per-category limits, groups, shared)** — `Budgets`, `CategoryBudgetLimits`, shared-budget sync. Far beyond PennyWise's `BudgetEntity`.
- **Multi-currency & exchange rates** — `Wallets.currency` + `cachedCurrencyExchange` + `pages/exchangeRatesPage.dart`. Equals `ExchangeRateEntity`.
- **Accounts & the balance line graph** — `Wallets` (= "Accounts" in UI) + `WalletDetailsLineGraph` (cumulative balance over time) + `createCorrectionTransaction()`. Don't add PennyWise's parallel `AccountBalanceEntity` table; instead *reconcile* Cashew's derived balance against the bank-reported balance (see the elevated section). Bank balances become first-class corrections, so the existing graph shows bank-true history for free.
- **Home-screen widgets** — `home_widget` + `HomePageWidgetDisplay` + `widgets/util/checkWidgetLaunch.dart`.
- **Export / backup / sync** — CSV + DB export/import **and** real Google-Drive multi-device sync with delete-logs (`struct/syncClient.dart`, `widgets/accountAndBackup.dart`). Ahead of PennyWise.
- **Categories (with sub-categories, icons, emoji)** — `Categories` table with `mainCategoryPk` hierarchy.
- **On-device LLM categorization & chat** — intentionally **not** wanted; deterministic parser + `AssociatedTitles` is the chosen strategy. Do not port `LlmRepository`/chat.
